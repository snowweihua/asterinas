## Findings
- PSCI CPU_ON returned `0x0` for CPUs 1, 2, and 3.
- With fallback gating, the kernel logged `PSCI succeeded for all CPUs, skipping fallback`.
- Hardware still timed out at `1/4` CPUs; AP output stopped at `A` in the latest run.
- The lock-marker run using AP `serial::send()` corrupted the shared UART stream; this is invalid runtime evidence and confirms UART output is unsafe for concurrent AP boundary markers.
- The UART-free telemetry run produced `TIMEOUT ... CPU0:s3` with no AP CPU stages, proving no AP reached `report_online_and_hw_cpu_id()`.
- The raw image disassembly showed the configured PA `0x344000` contains normal kernel code; the AP stub begins at raw offset `0x307000`, which corresponds to runtime PA `0x387000` when loaded at `0x80000`.
- With the corrected `0x387000` destination, both PSCI and forced fallback still produced `CPU1:s0 CPU2:s0 CPU3:s0`; no AP phase marker was observed.
- The MMU-state-aware marker run remained at `CPU1:s0 CPU2:s0 CPU3:s0`; forced fallback was then disabled again.
- Restoring hardcoded `0x344000` caused the BSP to stop before the copy-complete log because that address overlaps live SMP/kernel text in the current layout; the link-derived destination is required to avoid this overwrite regression.
- BISECT MILESTONE: clean HEAD (51434e9a, = ebedef32 + ap_early_entry markers) built and run on hardware reproduced the known-good behavior: serial printed `APRMBSDTXX012345` — AP enters ap_boot_entry, enables MMU, reaches ap_early_entry through init_on_ap, dies at enable_local (marker 6 absent). ebedef32 IS good; the regression is entirely in the uncommitted worktree changes.
- Evidence from the clean run: AP markers appeared AFTER the unconditional Trusted-Mailbox/mailbox/spin-table wake attempts (after `SMP bringup done`, TIMEOUT, and the PCI warning), suggesting the `fallback` wake path (BCM2836 mailbox write + dsb + sev, or TM) is what actually starts the parked APs. PSCI CPU_ON returning 0 does NOT itself start them. Prime suspect: my fallback-gating change skipping these writes.

### ROOT CAUSE CONFIRMED (single-variable bisect, 2026-09-01)
- Applied ONLY the fallback-gating edit to smp_rpi3.rs on an otherwise clean HEAD tree (19 insertions: psci_available/psci_all_cpu_on_success tracking + `run_fallback` gating that skips the TM/mailbox/spin-table wake sections when PSCI reports success).
- Result: PSCI CPU_ON returns 0x0 (SUCCESS) for all 3 CPUs, `skipping fallback` logged, TIMEOUT — only 1/4 CPUs online, and **NO AP markers at all** (no APRMBSDTXX012345). APs never enter ap_boot_entry.
- Clean-HEAD baseline (same kernel, PSCI also returns 0x0): `APRMBSDTXX012345` — APs DID enter ap_boot_entry.
- **CONFIRMED REGRESSION**: PSCI CPU_ON returning 0 (PSCI_SUCCESS) does NOT actually get the parked cores to jump to the entry point on this TF-A rpi3 build. The thing that actually wakes the APs is the UNCONDITIONAL fallback wake path (TM/mailbox/spin-table write + dsb + sev). My gating change skipped it because PSCI "succeeds", parking the APs permanently.
- **FIX**: Remove the gating. The fallback wake path must run unconditionally (regardless of PSCI status), matching the proven-good ebedef32 behavior.

## NEW BUG: AP crash at irq::enable_local() (marker 6) on known-good 51434e9a
Started: 2026-09-01
State: clean HEAD 51434e9a (committed b84cab67 documents the regression root cause; smp_rpi3.rs reverted to known-good). The AP now reliably enters ap_early_entry, prints markers `APRMBSDTXX 0 1 2 3 4 5`, then crashes in/around `enable_local()` — marker 6 never prints.

### Code path on the AP (ostd/src/boot/smp.rs ap_early_entry)
- marker 5 printed (after `crate::arch::init_on_ap()` = `bcm2836_irq::init_on_ap()` writes CNTPNSIRQ_BIT to this core's BCM2836 timer control reg)
- then `crate::arch::irq::enable_local()` — `msr DAIFClr, #0b0011` unmask IRQ+FIQ
- marker 6 never prints → crash is IN enable_local() or an IRQ firing immediately on unmask

### Key architectural facts gathered
- `enable_local()`: `mov x9,x30; msr DAIFClr,#0b0011; isb; mov x30,x9` — pure asm, safe.
- RPi3 IRQ vector: `irq_current` (trap/mod.rs:238) → `gic::acknowledge_interrupt()` → on RPi3 reads BCM2836 IRQ source (gic.rs:96-101) → dispatch `call_irq_callback_functions`.
- `bcm2836_irq::acknowledge_interrupt()` returns 30 (CNTPNS) if pending; `INNERS[30].callbacks` may be EMPTY because `timer::init()` runs on BSP AFTER `boot_all_aps()` → BSP hasn't registered timer callback yet during AP boot; the IrqLine 30 callback is registered later.
- `process()` with empty callbacks → just `interrupts_ack(30)` → returns. Benign in theory.
- **`bcm2836_irq::init_on_ap()` ARMS CNTPNSIRQ on the AP core. But whether the AP's physical timer actually FIRES depends on AP's `CNTP_CTL_EL0.ENABLE` (firmware/BL31 state). If left enabled, unmasking IRQ fires the timer immediately → entry into EL1 IRQ vector → dispatch.**

### HYPOTHESES (need runtime evidence to discriminate)
H1 [timer IRQ fires on unmask, dispatch to empty/global INNERS crashes]: distinguishing evidence = place a raw-PL011 marker at the very start of `irq_current` (and in `sync_exception_current`) to see WHICH exception type enters after enable_local. If an IRQ fires, distinguish: crash inside dispatch vs. IRQ storm re-entering.
H2 [synchronous fault, not IRQ]: AP accesses a per-CPU structure (e.g. set_this_cpu_id / CPU-local addressing) that faults under the AP's page table / CPU-local base. Distinguishing evidence = marker at start of sync_exception_current printing ESR/FAR; if sync fires with a specific ESR, this is it.
H3 [FIQ pending / peripheral IRQ storm]: U-Boot left a peripheral IRQ/FIQ enabled; on unmask a non-timer FIQ/IRQ storms. Distinguishing evidence = the BSP masked all peripherals in init_on_bsp, but the AP core's BCM2836 timer control was just re-armed; if FIQ fires, check FIQ_CONTROL on AP.

### PLAN (evidence first, journal-then-modify)
1. Add raw PL011 marker at start of `irq_current` and `sync_exception_current` (both already have raw helpers in trap/mod.rs). This tells us exception class.
2. Additionally print ESR/FAR from sync handler for H2; print IRQ source value at irq_current start for H1.
3. Also test a controlled fix variant for H1: DON'T arm CNTPNSIRQ in `bcm2836_irq::init_on_ap()` (make AP timer IRQ arming deferred), OR ensure AP's CNTP_CTL_EL0 is disabled before enable_local. This is the cleanest test because it toggles the suspected cause.

### Experiment 2 RESULT (2026-09-01): AP freezes in IRQ dispatch after acknowledge
- Refined irq_current markers: `[IRQ`, then on Some: `:` + raw_put_hex(irq_num) + `:D]` + call_irq_callback_functions + `[RET]`; on None: `:NONE]`.
- Serial: `APRMBSDTXX012345[IRQ:` then NOTHING more (empty reads, AP frozen).
- `acknowledge_interrupt()` returned Some(irq_num) (the `:` printed). `raw_put_hex` uses the identical PL011-write mechanism as raw_puts (which worked for `[IRQ`), so a fault there is unlikely; the AP is frozen somewhere in/after the acknowledge+dispatch region.
- NOT a sync exception (no [SYNC]); NOT rpi-timer-only (experiment 1 disabled it and IRQ still fired).
- Strong hypothesis: `call_irq_callback_functions` (dispatch to INNERS[irq].callbacks + InterruptLevel per-CPU tracking + bottom_half) touches CPU-local/shared state not ready on the AP, OR the IRQ fires before `activate_kernel_page_table()` and the handler faults on kernel-high-half access. Also matches the observed mystery: `serial::send` letters (A-H) never print on the AP though raw markers do — AP-side shared/per-CPU state isn't ready.

### Experiment 3 (next, decisive): skip dispatch on a toggle
- Modify irq_current: on Some(irq), print ONE char for class (T=30 timer, V=27 virt timer, G=gpu, O=other) and SKIP call_irq_callback_functions (just err or return), then let ap_early_entry continue to marker 6/7/8.
- If AP reaches marker 6/8 and comes online → crash IS in dispatch (per-CPU/shared state). Fix: defer IRQ enable on AP until per-CPU interrupt state is ready (mirror x86 timer::init_on_ap), or make dispatch AP-safe.
- If AP still freezes even with dispatch skipped → crash is in acknowledge/reading BCM2836 source or the IRQ vector entry itself.

### Experiment 3 RESULT (2026-09-01): IRQ STORM on all APs + ROOT CAUSE FOUND
- Removed dispatch (skip call_irq_callback_functions). Result: APs flood `[IRQ` markers endlessly → INFINITE IRQ STORM (multiple APs interleaving on shared UART = garbled output). `Only 1/4 CPUs online`.
- Storm proves: an IRQ fires on each AP right after `enable_local()`, and since `acknowledge_interrupt()` only READS (never clears) the source and `end_interrupt()` is a no-op (bcm2836_irq.rs:298), the IRQ re-fires forever → locks up each AP.
- Authoritative BCM2836 register map (RPi3 Peripherals PDF + Linux irq-bcm2836.c) confirms TWO root causes:
  1. **BUG: wrong per-core stride.** Code uses `CORE_REG_STRIDE = 0x400` for timer/mailbox-control/IRQ-source, but the REAL per-core stride is `0x4` (Core0 Timer Ctrl=0x40, Core1=0x44...; Core0 IRQ Src=0x60, Core1=0x64...; Core0 Mailbox Ctrl=0x50, Core1=0x54...). AP core c>0 read/write wrong regs (e.g. core1 IRQ source at 0x460 instead of 0x64) → acknowledge returns 0 for the real pending IRQ → storm. Only core0 ever worked because 0x400*0=0. Mailbox SET/CLR use a DIFFERENT stride (0x10/core): e.g. CORE1_MBOX3_SET=0x9C, CORE{n}_MBOX3_CLR=0xCC+0x10*n.
  2. **Pending wake mailbox IRQ never cleared.** Kernel wakes APs via MAILBOX3 set (boot log: `wrote mailbox@0x9c/0xac/0xbc=0x344000`). This leaves CORE{n}_MAILBOX3 pending (bit7 of IRQ source). On enable_local it fires; nothing clears it → storm.
- FIX DESIGN (in bcm2836_irq.rs):
  - Correct per-core stride to 0x4 for timer/mailbox-control/irq-source (keep explicit CORE*_MAILBOX3_SET at 0x8C+0x10 for set/clear).
  - In `init_on_ap`: mask ALL local IRQs for this core (timer ctrl=0 + mailbox ctrl=0), clear pending wake mailbox3 (write CLR), disable physical timer (cntp_ctl_el0=0). So no stray IRQ can fire at enable_local.
- Coincides with observed mystery: `serial::send` letters never appear on AP (shared/per-CPU state + wrong regs).

### Experiment 4 RESULT (2026-09-01): IRQ STORM FIXED, now a SYNC exception after marker 5
- Applied real fix to bcm2836_irq.rs:
  - Corrected CORE_REG_STRIDE 0x400 → 0x4 (authoritative per-core stride).
  - init_on_ap now masks ALL ARM-local IRQ sources for the core (timer ctrl=0 + mailbox ctrl=0) + clears pending wake mailbox3 (C0RCH3 CLR at 0xCC+0x10*core) + disables physical timer.

### ROOT CAUSE #2 (2026-09-01): AP stub zeroes SHARED kernel BSS — explains mutual exclusion
- USER CLUE: Two cases are mutually exclusive across many runs:
  - Case A: asterina banner + `~ #` shell appears → NO `APRMBSDTXX` at all → APs never entered the stub.
  - Case B: `APRMBSDTXX` appears (APs are running) → NO banner/shell later → BSP hangs.
- FOUND IT in `ostd/src/arch/aarch64/boot/ap_boot.S` lines 91-101 (present since cedcff49):
  ```asm
  /* Zero BSS for this CPU */
  ldr x0, =__bss        /* high-half VA of the SHARED kernel BSS */
  ldr x1, =__bss_end
 1: str xzr, [x0], #8   /* wipes EVERY kernel global the BSP initialized */
  ```
- BSP cold-boot zeroes BSS once in boot.S:574-584, then Rust initializes globals in it
  (HW_CPU_ID_MAP, Once flags, IRQ callback table, allocator, cpu-local map, boot io, etc.).
- Every AP that wakes re-zeroes that SAME shared memory while the BSP runs → destroys BSP state.
- EXPLAINS EVERYTHING:
  - Case B (`APRMBSDTXX`, no shell): APs wake → wipe BSS → BSP breaks on wiped globals before the
    banner (no shell), AND each AP later faults because irq_current/handler reads the wiped IRQ
    callback table → the `[SYNC]` we saw. APs themselves also die on zeroed globals.
  - Case A (shell, no markers): APs never actually woke → BSS intact → BSP boots to shell cleanly.
  - Also explains earlier `[SYNC]`/freeze-after-marker-5: the wake mailbox3 IRQ now correctly masked,
    but the BSS-wiped IRQ table on the AP makes dispatch fault (sync abort), not an IRQ storm.
- x86 AP stub has NO BSS zeroing — only aarch64's had this copy-paste bug.
- FIX: removed the BSS-zero block (and its B/S markers) from ap_boot.S; also removed the
  core-1-only gate in smp.rs ap_early_entry (no longer needed to keep UART readable).
