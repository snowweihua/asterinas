## Hypotheses
1. [PENDING] Unpacking hang = per-CPU frame/heap allocator cache refill race
   under timer IRQ on an AP; `collect_pages` loops acquiring pages and an AP
   stuck in an IRQ/lock state starves it. Evidence: marker at page-commit loop.

   Evidence: vary entry position across boots.

   init stack region not mapped into kernel TTBR0/VMAR (ex_table miss
   instead of VMAR PML4 walk). Evidence: fault is level-0, addr is user-region.

### Agent reports (2026-09-16, code-map before marker build)
- **Write path (ramfs->page-cache)**: `InodeWriter::write` -> `RamInode::write_at`
  (ramfs/fs.rs:1023, takes `page_cache.lock()` + `inode_meta.lock()`) ->
  `PageCache::write` -> `Vmo::write` -> `write_anonymous_pages`
  (vmo/mod.rs:671) -> `collect_pages` (vmo/mod.rs:773, `'retry` loop bounded
  by `current_range.start >= range.end`) -> `try_operate_on_range_internal`
  (vmo/mod.rs:425, bounded `for _ in page_idx_range`) ->
  `commit_on_anonymous` (vmo/mod.rs:309, XArray `self.pages.lock()`) ->
  `CachePage::alloc_zero()` -> `FrameAllocOptions` frame alloc.
  **The write path itself issues NO TLB flush / IPI.**
- **TLB flush / IPI**: `dispatch_tlb_flush` (ostd/src/mm/tlb.rs:82) pushes
  ops to per-CPU `FLUSH_OPS` and calls `inter_processor_call`; actual wait is
  deferred to `sync_tlb_flush` (tlb.rs:137) -> `PendingIpis::wait`
  (ostd/src/smp.rs:77) spins on per-CPU `HAS_PENDING_IPIS` AtomicBool
  (set smp.rs:127 Release, cleared do_inter_processor_call smp.rs:173).
  RPi3 IPI send = mailbox-0 doorbell (bcm2836_irq.rs:384); receive via
  `CORE0_IRQ_SOURCE` bit4/CLR (bcm2836_irq.rs:287-291, 330-336). APs enable IPI
  IRQ in `init_on_ap` (bcm2836_irq.rs:210) BEFORE `enable_local()` — ordering OK.
- **Allocators**: frame per-CPU cache (osdk/deps/frame-allocator/src/cache.rs)
  is `RefCell<<CacheOfSizes>>` under `DisabledLocalIrqGuard`; refill
  `pools::alloc` -> `LOCAL_POOL` RefCell or `GLOBAL_POOL`
  `SpinLock<BuddySet, LocalIrqDisabled>` (pools/mod.rs:24). Heap per-CPU pool
  ALso RefCell under irq guard, `GLOBAL_POOL` SpinLock<Heap, LocalIrqDisabled>.
  O(n) loops (buddy coalesce, alloc_chunk search, slab cursor_mut_at) are
  bounded by MAX_ORDER / guarded early-exits. Deadlock risk exists only if a
  holder of GLOBAL_POOL (IRQs off) waits on an IPI-completing CPU that is
  itself spinning on GLOBAL_POOL.
- **Key negative**: no `TLB`/`SCH` marker appears AFTER `[kernel] unpackin...`
  in the last capture — so the hang is NOT (evidently) an in-progress TLB
  flush broadcast from the unpack thread.

## Root Cause: KPT Root Frame Corruption
The KPT singleton root frame at PA 0x6f8000 was corrupted after activation.
PGD[256] (linear window) and PGD[448] (frame-meta window) were cleared to
zero while PGD[511] (kernel window) remained intact. This is impossible for
any legitimately-built page table. The frame content was overwritten at runtime,
likely by the frame allocator double-issue, cache coherency, or DMA corruption.
The corruption is non-deterministic (6 faults on one boot, 0 on five subsequent
boots), ruling out a deterministic build/logic bug.

## Final fix
The R47-R48 investigation retained the R45/R46 fixes (dump_act_log removal from
the trap path and userspace fault path), which eliminated the spurious
fault-dump noise on the lossy RPi3 UART. The root frame corruption at
PA 0x6f8000 was root-caused (PGD[256]/[448] cleared, PGD[511] intact) but the
exact overwrite source was not pinpointed, as the fault is non-deterministic
and no reproduction could be captured. No speculative fix was applied.
