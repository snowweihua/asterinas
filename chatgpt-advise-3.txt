## The suspicious part: `PSCI_CPU_ON` → `INVALID_PARAMETERS`

On a normal PSCI implementation, the call is essentially:

```text
CPU_ON(
    target_cpu,
    entry_point,
    context_id
)
```

and TF-A validates the target CPU and entry point.

If you're doing:

```text
target = MPIDR_EL1 CPU1
entry   = 0x344000
```

and getting:

```text
PSCI_E_INVALID_PARAMS
```

I would **not assume that 0x344000 is an invalid address** yet.

There are several possibilities:

```text
PSCI_CPU_ON
   │
   ├── wrong MPIDR?
   │
   ├── CPU already considered ON?
   │
   ├── entry point violates TF-A validation?
   │
   ├── wrong execution/security state?
   │
   ├── TF-A RPi3 platform expects a special handoff?
   │
   └── wrong PSCI calling convention?
```

And because you get the same error for every entry point, the **target CPU / PSCI state** is especially interesting.
