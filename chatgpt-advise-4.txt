# There's another thing I would investigate immediately

The summary says:

> TF-A calls PSCI_CPU_ON to release secondaries from wait loop

I would challenge this.

The architecture is more subtle.

There are two different contexts:

```text
             CPU1
              │
              ▼
        armstub8 startup
              │
              ▼
       secondary waiting
              │
              │
       TF-A takes over
              │
              ▼
        BL31 secondary
              │
              ▼
       eventual BL33/kernel
```

The **PSCI `CPU_ON` interface is intended for the OS to request a powered-off CPU be brought online**.

It isn't simply:

```text
PSCI_CPU_ON()
     ↓
wake armstub WFE
```

So don't let OpenCode model the system as "PSCI is another way to write `0xe0`."

It's a different CPU lifecycle.

# One particularly important possibility

Your boot chain may have an **unexpected TF-A configuration**.

For example, you may effectively have:

```text
start.elf
   ↓
armstub8
   ↓
BL31
   ↓
U-Boot
   ↓
Asterinas
```

but the `armstub8.bin` you're using might have been built with assumptions intended for the standard Linux/U-Boot boot flow.

Then you have:

```text

    Linux/U-Boot integration
       ↓
    secondary CPU handoff

Asterinas expects:
    DT spin-table
       ↓
    secondary CPU handoff
```

Those assumptions don't necessarily match.

That would explain why:

```text
spin-table write = successful
PSCI_VERSION     = successful
PSCI_CPU_ON      = NOT_SUPPORTED
APs              = never arrive
```
