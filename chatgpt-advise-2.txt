I would **not commit the spin-table fix as the final SMP solution yet**, and I would **not jump to a VC mailbox implementation either**.

Your new evidence changes the diagnosis in an important way: **the spin-table write is correct, but we haven't yet established that the CPUs reaching Asterinas are actually the CPUs that `armstub8` parked in its spin-table loop.**

More importantly, I checked the current TF-A Raspberry Pi 3 documentation, and it strongly supports your suspicion about the boot chain—but with an important correction.

### The key point

TF-A's RPi3 port explicitly says:

* all cores start at address 0 when `armstub8.bin` is used;
* TF-A has a **secondary-core warm-entry mailbox**;
* secondary CPUs wait there during cold boot;
* once BL31 is ready, the primary must use **`PSCI_CPU_ON` to release secondary CPUs**;
* after that, the secondary cores can be directed to the kernel through another mailbox mechanism. ([GitHub][1])

So this part of your session-context conclusion is essentially right:

> The spin-table at `0xe0/e8/f0` is not necessarily the mechanism responsible for releasing the CPUs from their current state.

And this is particularly significant:

> **TF-A's RPi3 implementation explicitly supports PSCI and recommends/uses PSCI for secondary CPU startup.** ([tf-a.docs.trustedfirmware.org][2])

There is even a TF-A discussion specifically saying that **RPi3 is an upstream example where PSCI is recommended even when the underlying platform may use a spin-table-like mechanism**. ([lists.trustedfirmware.org][3])

# Don't implement VC mailbox yet

This is where I would disagree slightly with your proposed option 2.

The TF-A documentation says there are **two different mailbox concepts** involved:

```text
             TF-A
              │
       ┌──────┴──────┐
       │             │
 cold boot       post-BL31
 mailbox          mailbox
       │             │
       ▼             ▼
secondary       kernel/AP
wait state      handoff
```

TF-A itself uses a **Trusted Mailbox in shared BL RAM** during cold boot, and then PSCI `CPU_ON` releases the secondary CPUs. ([tf-a.docs.trustedfirmware.org][2])

That's quite different from saying:

> "Asterinas needs to talk directly to the VideoCore mailbox."

I would **not bypass TF-A and talk to the VC firmware yet**.

That would give you:

```text
Asterinas
   ↓
VC mailbox
   ↓
VideoCore firmware
   ↓
CPU power control
```

while you already have:

```text
Asterinas
   ↓
SMC
   ↓
TF-A
   ↓
PSCI
```

The second path is much cleaner.

```text

x1 = MPIDR of CPU1
x2 = entry address
x3 = context ID
```

The standard PSCI DT binding describes `cpu_on` and the SMC/HVC calling convention. ([GitHub][5])

# The DTB is another very important clue

Look at what your actual DTB says.

If it currently contains:

```dts
cpu@1 {
    enable-method = "spin-table";
    cpu-release-addr = <0x0 0xe0>;
```

then Asterinas is being told:

> "You are responsible for releasing CPU1 using spin-table."

But if TF-A is providing PSCI, what we really want is something like:

```dts

    enable-method = "psci";

```

and similarly for CPU2/CPU3.

Linux's DT binding explicitly supports `psci` as the AArch64 CPU `enable-method`. ([GitHub][6])

So **the DTB may currently be telling Asterinas to use the wrong CPU bring-up mechanism.**

That could explain almost the entire situation.

# One more important correction to the session context

I would change this statement:

> "RPi3 secondary CPUs are managed by the VC firmware and cannot be woken via ARM_LOCAL spin-table alone."

to something more precise:

> **On the TF-A RPi3 boot path, secondary CPU startup is mediated by TF-A/PSCI; therefore writing the Raspberry Pi armstub spin-table does not necessarily release CPUs that have already transitioned into TF-A's secondary-core wait state.**

That's a much safer conclusion.

The distinction matters because the official `armstub8.S` absolutely does contain a spin-table loop:

```asm
secondary_spin:
    wfe
    ldr x4, [x5, x6, lsl #3]
    cbz x4, secondary_spin
```

with the release slots at `0xe0`, `0xe8`, and `0xf0`. ([GitHub][7])

So the spin-table itself isn't bogus. **Your observation is that your CPUs aren't currently executing that loop anymore.**

That's the critical insight.
